# Repository Group for Github

A cross-browser extension (Chrome, Edge, Brave, Firefox) that organizes the repositories of a GitHub organization into **groups and subgroups**, the way GitLab does (`climate / science / carbon-science`). It runs on github.com, needs no server, and keeps the group structure in the organization's own `.github` repository so every member sees the same tree.

This file is the build spec. The `design/` folder holds an interactive mockup that is the source of truth for look and behavior. When this file and the mockup disagree, ask the user.

## 1. Decisions already made (do not reopen)

| Topic | Decision |
|---|---|
| Product name | **Repository Group for Github**. Use this exact spelling (lowercase "h") everywhere: manifest `name`, store listings, UI, README. Short name / badge: `RG`. If a store reviewer rejects the spelling, stop and ask the user. Do not rename on your own. |
| Form factor | Browser extension only. **No self-hosted app, no backend, no database, no analytics.** |
| Browsers | Chrome, Edge, Brave (one Chromium MV3 build) and Firefox (MV3 build). Safari is out of scope. |
| Where it runs | Inside github.com pages, injected into GitHub's own UI. Not a separate website. |
| Default view | Opening `https://github.com/orgs/<org>/repositories` shows the **grouped view immediately**. A toggle returns to GitHub's native list. |
| Group URLs | `https://github.com/orgs/<org>/repositories#<group>/<subgroup>` (hash). Do **not** use `/orgs/<org>/<group>`: those paths belong to GitHub (`/people`, `/teams`, `/projects`, `/settings`, …), would 404 first, and could collide. |
| Shared storage | `repo-groups.yml` in the org's `.github` repository (`<org>/.github`). Logos go to `logos/` in the same repo. |
| Theme | GitHub's default light and dark themes, by reading GitHub's Primer CSS variables (see `design/tokens.css`). |
| UI language | English, to blend with GitHub. Set up i18n (`_locales/en`) so `pt_BR` can be added later. |
| Weight | Must be **very light and small**. See the budgets in §10. |
| Teams | Groups and subgroups can be tagged with **GitHub teams** (inherited by subgroups). The extension shows them, organizes the team's repositories page, pre-selects teams on New repository, and offers **Sync access**: it shows which repos a tagged team lacks access to and grants it in one click. **Only adds or raises access, never removes or lowers it.** (F12) |
| Large orgs | Two layers. **Org file** (`repo-groups.yml`, shared, rule-based, stays small even with thousands of repos) + a personal **My groups** layer per user (only the repos they want to classify, stored in the browser). Repos are indexed per user through the API with an incremental cache. An index generated by a GitHub Action **ships in v1** but stays **opt-in** (off until the org sets `index: action`). (F13, F14) |
| Members without admin rights | Fully supported (**F15**). They see and organize **only the repositories they can access**. The org file is read-only for them unless they can write to `<org>/.github`. They organize in **My groups**, and can **suggest** changes to the org file through GitHub's own "Propose changes" flow. Nothing in the extension requires org owner rights, except installing the GitHub App once. |
| Fork rules (A5) | `match` accepts `fork-of:<owner>` and `fork-of:<owner>/<repo>` (forks by upstream; parent stored in the index as `parent: "owner/repo"`, read lazily by GraphQL). The Ungrouped tab has **Auto-group forks**, which only opens the F8 editor with a draft. Code: `core/fork-groups.ts`, `background/parents.ts`. |
| Who runs Sync access | **Both** org owners (can update every repository) and repository admins (can update the repositories they administer). The UI must support both cases (F12). |

## 3. Market context (why this exists)

Similar extensions exist, but all are small and limited:
- **GitFolders** (Chrome only, ~42 users, paid, syncs through its own server, flat folders).
- **GitHub Repo Folders** (~7 users, flat, browser-local).
- **Tab Groups for GitHub** (~9 users, flat tabs, browser-local, Chrome only).

GitHub itself has no repo folders. The community request has 400+ votes and no commitment.

Our differentiators, which must not be lost:
1. **Nested** groups (GitLab-style hierarchy).
2. **Shared with the whole org** via a versioned file in `.github`. Not per-browser.
3. **Rule-based** placement (`dags-*`), so new repos file themselves.
4. **AI round-trip**: export YAML + prompt, paste the answer back, review the diff, commit.
5. Cross-browser, tiny, no server.

  - the **list box**.
- **List rows:**

  - A **repo row** has the repo icon, name, a Public/Private label, a description, and meta: language dot, forks, stars, open issues, open PRs, "Updated X ago". Repo name links to `https://github.com/<org>/<repo>`.
  - Children are indented 28px per depth level (16px on narrow screens).

- Above the list, a one-line **index status** (F14): "45 repositories · updated just now · Re-index", or a progress state while indexing.
- A **segmented control** at the top of the content switches between **Org groups** and **My groups** (F13).
- On the root, ungrouped repos are listed after the groups, and the *Ungrouped* tab lists only them.
- **Search:**
  - filters across the current group recursively;
  - matches repo name and description;
  - shows results flat, with a muted `group / subgroup /` prefix.
  - The `/` key focuses the search (only when the user is not typing in a field).
- Expanded/collapsed state per org is remembered in `storage.local`. `infra`-style first-level groups start collapsed except the first one.
- Repos are sorted by last push (newest first), matching GitHub's default "Last pushed".
- **Done when:** with the example YAML, the root shows `infra` and `ai`, with `keep_alive_job` ungrouped. Hash `#infra/dagsrv` opens the dagsrv page with `dagsrv`, `dags-repo`, `kite-dagsrv`. Browser back/forward moves between groups.

### F5 — Edit group drawer (right side, 480px, full height)
- **Fields:**
  - **Logo** (F7);
  - **Name**: slug, lowercased; non-slug characters become `-`. A hint shows the full path;
  - **Description**;
  - **Teams** (org layer only, F12): chips for this group's own teams, each with a permission select (Read, Triage, Write, Maintain, Admin) and ×, plus **Add team** (a picker of the org's teams). Inherited teams show read-only and muted, e.g. "core_team · Write · from infra";
  - **Match rules**: chips with ×, plus an input that adds on Enter;
  - **Matching repositories (n)**: a live list. It marks repos that currently sit in another group with "now in x/y";
  - a link **Edit .github/repo-groups.yml** that opens F8 with this draft included;
  - at the very end, a quiet red row **Delete this group / subgroup** with a **Delete…** button (edit mode only, not in F6).
- **Footer:** "Saved as a commit to `<org>/.github`…", **Cancel**, **Save changes**.
- **Validation:**
  - the name is required;
  - no duplicate name among siblings. The error reads "A group named "x" already exists here."
- Saving commits the YAML (§7) and shows a toast: "Committed to `<org>/.github/repo-groups.yml`".
- Esc or a click on the backdrop closes the drawer.
- **Delete group:** **Delete…** opens a GitHub-style confirmation (`role=alertdialog`) titled "Delete `<org> / <path>`": the group, how many subgroups, rules and repositories it holds, and where those repositories go. The red button **I want to delete this group/subgroup** stays off until the person types the group's full path (`infra/dagu`). Esc, Cancel or the backdrop close only the confirmation.
  - One commit to `repo-groups.yml` (`chore(repo-groups): delete group infra`). The group and all its subgroups are removed. **No repository is deleted.**
  - **A subgroup:** its match rules, and those of its own subgroups, move to the parent's `match`, so its repositories stay in the group above.
  - **A top-level group:** nothing moves up; its repositories become Ungrouped unless another group's rules catch them.
  - Team tags of the removed groups go away but access already granted on GitHub is not revoked; logo files stay in `<org>/.github/logos`. The confirmation says so when it applies.
  - Afterwards the page goes to the parent group (or the top level) when it was showing the deleted group, and the toast reads "Deleted infra/dagu · committed to …".

### F7 — Group logos
- **Sources:**
  - **Upload image** (file picker, `accept="image/*"`);
  - drag & drop onto the logo box;
  - paste an image from the clipboard;
  - **Paste a link**: a URL input plus **Load**.
- **Limits:**
  - PNG, JPG, SVG or WebP, up to 5 MB;
  - errors are shown inline in plain language (see mockup copy).
- **Cropper:**
  - square canvas: 280 logical px, a 240px crop square with 18% corner radius;
  - outside the crop square is dimmed with `--rg-crop-dim`;
  - drag to pan; zoom 1×–5× with a slider and the mouse wheel; arrow keys pan and `+`/`-` zoom;
  - the image always covers the crop square (clamped);
  - **Use this crop** produces a **192×192 PNG**;
  - **Cancel**.
- **Use the letter instead** removes the logo.
- **Storage:**
  - on save, commit the PNG to `<org>/.github` at `logos/<group-path-with-dashes>.png` (e.g. `logos/infra-dagsrv.png`);
  - set `logo:` in the YAML in the **same commit** (§7).
- **Display:**
  - the `.github` repo may be private, so `<img src="https://raw.githubusercontent…">` will not work;
  - fetch logos through the API with the user's token in the background worker;
  - cache them as data URLs in IndexedDB, keyed by blob SHA;
  - if a logo fails to load, fall back to the letter avatar.
- **External links:**
  - fetch the image in the background worker, so CORS on the image host does not block the canvas;
  - request the optional host permission for that origin with `permissions.request()` inside the click handler, which counts as a user gesture;
  - if the user declines, show: "Allow access to <host> to load this image, or download it and upload the file."
- Logos appear in the header, breadcrumb, group rows, sidebar tree (16px) and the New repository picker.

     - **[Copy prompt for AI]** and **[Copy YML]**: joined split buttons.

### F11 — Data loading and caching
- **Repo list:** the repo index from F14 (REST pages in parallel + incremental refresh). Render from the index instantly, then refresh in the background (stale-while-revalidate). The default refresh interval is 5 min.
- **Config:** read `repo-groups.yml` via `GET /repos/{org}/.github/contents/repo-groups.yml`, keeping the `sha`. Cache it with an ETag (`If-None-Match`) to save rate limit.
- **Teams data** (F12): the org's teams and each tagged team's repository access, cached per org with the same refresh interval.
- Show the index status line (F1). Never block rendering on the network when a cache exists.

### F12 — Teams on groups, team pages and Sync access
**Why:** today the user gives each team access to each repository by hand. With teams tagged on groups, the extension knows which team should reach which repo and can grant the missing access in one click.

- **Tagging** (YAML in §5.1, UI in F5):
  - a group lists teams, each with a permission;
  - subgroups **inherit** the teams of all their ancestors;
  - the **effective teams** of a group = its own + inherited; when the same slug appears more than once, the one closest to the group wins (a subgroup can raise or lower the permission its parent set).
  - A repository's **target access** = the effective teams of the org group it is placed in (placement algorithm, §5.3). Ungrouped repos have no target.
- **Where teams show:**
  - chips in group headers and rows (F1);
  - the Teams section of the sidebar (F2);
  - the Teams field of Edit group (F5);
  - the Teams field of New repository (F9).
- **Team repositories page** — `https://github.com/orgs/<org>/teams/<slug>/repositories`:
  - Keep GitHub's team header and team tabs. Replace the repository list with the grouped view (same components as F1).
  - Show **only the repositories this team can access**, placed in the org's group tree. Groups with no accessible repos are hidden.
  - On each repo row, the label shows the team's permission there (Read, Triage, Write, Maintain, Admin) instead of Public/Private.
  - Groups tagged with this team get a highlighted team chip.
  - Banners at the top, only when they apply:
    - "**N repositories** in groups tagged `<slug>` don't give it the access set in repo-groups.yml. **Review & sync**" (accent banner);
    - "**M repositories** this team can access are in groups not tagged for it." (neutral, informational; a link expands the list). The extension never removes this access.
  - A list/grouped toggle exactly like F4.
- **Sync access drawer** — opened from the banner, from a team chip menu, or from **Edit group → Teams → Sync access**:
  - **One row per (repository, team)** where the current access is lower than the target. Columns: repo, team, current (`none`, `Read`, …), target. Each row has a checkbox, checked by default.
  - The header reads "Give core_team access to 5 repositories".
  - **Grant access** applies the checked rows with `PUT /orgs/{org}/teams/{slug}/repos/{org}/{repo}` and body `{"permission": "<target>"}`, 3 at a time, with a progress bar and a result per row ("Granted", or the error).
  - **Never** removes a team, and never lowers a permission. If the current access is higher than the target, the row does not appear.
  - **Errors:**
    - 403/404: "You need admin access to this repository — ask an org owner". The other rows continue.
    - 422 (the repository is not owned by the org or a direct fork of one of its repos, or the team cannot be added): show GitHub's message.
    - 403 right after the App's permissions changed: show the "an org owner must accept the update" message from §6.
  - After finishing, refresh that team's access cache and the page.
  - Both org owners and repository admins can use it (§6). If the user is not an org owner, show a note above the list: "You can update the N repositories you administer. Org owners can update all of them." Rows the user cannot apply start unchecked (§6).
- **Data needed:**
  - the org's teams;
  - for each team that appears in the YAML, its repositories with permission.

  Both come through GraphQL (§8), paginated, cached per team. **Do not** make one request per repository to read access.
- **Done when:**
  - Setup: `infra` is tagged `core_team` (Write). core_team already has Write on `dagsrv` and `kite-dagsrv`, Read on `authn`, and nothing on `dags-repo`, `kite-authn`, `kite-cmonitor`.
  - The team page then shows the banner "4 repositories…", and Sync access lists exactly those four rows (authn as Read → Write).
  - Granting them leaves `keep_alive_job`, which the team can access outside its groups, untouched.

### F13 — My groups (personal layer)
**Why:** in orgs with hundreds or thousands of repositories, one person usually cares about a few dozen. They need their own organization without changing the shared structure.

- **Same schema** as `repo-groups.yml` (§5.1), with two differences:
  - no `teams` key (teams are org-level);
  - no logo files in a repo (logos are stored as data URLs in the same storage, max 192px PNG).
- **Storage:** `storage.sync`, key `mygroups:<org>`, so it follows the user across their browsers. If the serialized YAML exceeds the sync quota (about 8 KB per item and 100 KB total), split it across items. If that is not enough, fall back to `storage.local` and show a "Not synced — too large" note in Options.
- **Independence:** a repository can be in an org group **and** in a personal group. The placement algorithm runs separately for each layer.
- **UI:**
  - The **Org groups | My groups** segmented control (F1) switches the whole page between the two trees.
  - Every feature works on the personal layer: Edit group, New group, logos, the YAML editor with AI (title "My groups (personal)", the button reads **Apply and save**, the footer says "Saved in this browser and synced with your browser account.").
  - Group URLs for the personal layer use `#~my/<path>`.
  - On the personal root, the "Ungrouped" tab is named **Not in My groups**.
  - **Add to My groups…**: a "⋯" menu on every repo row (both layers) opens a small picker of personal groups plus "New personal group". It adds the exact repo name to that group's `match`.
  - **Bulk classify:** in search results, each repo row gets a checkbox; a bar appears with "n selected · **Add to My groups…**".
- **Options page:** **Export** (download `my-groups-<org>.yml`) and **Import** (file picker, validated like F8).
- **Done when:** a user with an org of 3,000 repos can search "billing", select 12 results, add them to a new personal group "billing", and see that group in the sidebar on another browser signed into the same browser account.

### F14 — Large organizations (hundreds to thousands of repositories)
**Goal:**
- the first visit to a 3,000-repo org shows groups within a few seconds, filling in progressively;
- every later visit renders from the local index instantly, refreshing with 1–2 requests.

- **The org YAML stays small.** It holds rules, not a list of every repository, so it does not grow with the org. Exact names are added only when someone overrides placement. The repository data lives in the local index, not in YAML.
- **Local index** (IndexedDB, database `rg`, store `repos:<org>`):
  - fields per repo: `name, description, language, languageColor, private, archived, fork, pushedAt, stars, forks, openIssuesAndPrs, viewerIsAdmin` (`viewerIsAdmin` comes from `permissions.admin` in the REST response and drives which Sync access rows the user can apply);
  - about 200 bytes each, about 1 MB for 5,000 repos;
  - plus metadata: `lastFullSync`, `lastIncrementalSync`, `total`.
- **First index:**
  1. `GET /orgs/{org}/repos?type=all&sort=pushed&direction=desc&per_page=100&page=1`.
  2. Read `Link: rel="last"` to learn the page count, then fetch the remaining pages **in parallel**, 6 at a time.
  3. After each page: store it, recompute placement and update the view. Already-rendered groups simply gain repos.
  4. Show progress in the index status line: "Indexing 1,200 of about 3,400 repositories…".

  Example: 3,400 repos = 34 requests ≈ 6–10 s, only once.
- **Incremental refresh** (every visit after the refresh interval):
  - fetch page 1 sorted by `pushed` desc;
  - continue to the next page only while every repo on the page has `pushed_at` newer than `lastIncrementalSync`;
  - merge into the index. Usually 1 request.
- **Full reconciliation** (catches renames, deletions, visibility and archive changes, which do not change `pushed_at`) runs in the background:
  - at most once every 24 h;
  - or when the incremental refresh sees a total different from the stored one;
  - or when the user clicks **Re-index**.
  - Same parallel fetch; replace the index atomically at the end.
- **Detail counts:**
  - REST gives `open_issues_count`, which includes PRs. The stats row shows **Open issues & PRs** with that number;
  - for groups with 200 repos or fewer, load separate issue and PR counts lazily with GraphQL (aliases, 50 repos per query) and split the stat into **Open issues** and **Open pull requests**.
- **Rendering at scale:**
  - first-level groups start collapsed when the org has more than 200 repos;
  - any list longer than 100 rows is **virtualized** (simple windowing written in the project, no library);
  - rule regexes are compiled once per config version;
  - placement is memoized by (config sha, index version);
  - search runs in memory over the index (names + descriptions), with a 100 ms debounce;
  - the sidebar tree shows counts from the memoized placement.
- **Rate limits:** read `X-RateLimit-Remaining`. Below 200, pause background work, keep showing cached data and say "Paused to respect GitHub's rate limit — resumes at HH:MM".
- **Index generated by a GitHub Action** (ships in v1, opt-in, off until `index: action` is set):
  - template in `design/actions/repo-index.yml`;
  - it runs hourly in `<org>/.github` with an org-level token and writes `repo-index.json` (same fields as the local index);
  - the extension uses it **only** when `repo-groups.yml` has `index: action`: it downloads that one file instead of doing the first parallel index, then applies the incremental refresh on top.
  - `viewerIsAdmin` depends on who is looking, so it is not in `repo-index.json`. The extension fills it in with its own API calls, and only when Sync access opens.
  - **Privacy warning** (show it in the docs and in Options next to the setting): everyone who can read `<org>/.github` can read the names and descriptions of **all** repositories in the file, including private ones they cannot open. Only enable it in orgs where members already see every repository.
- **Done when:** with a mocked org of 3,000 repos, the first index finishes in under 10 s with visible progress. A reload renders from cache in under 150 ms. An incremental refresh with no new pushes makes exactly 1 request.

### F15 — Members without admin rights (limited access mode)
**Why:** most people in an organization are not org owners and cannot write to `<org>/.github`. They still need to organize the repositories they work on. The extension must be fully useful to them, limited to **the repositories they can access**, without asking anyone for extra rights in everyday use.

**What a regular member can do:**
- see the grouped view, built only from repos they can access;
- organize everything in **My groups**;
- suggest changes to the org file;
- create repos in a group;
- Sync access only on repos they administer.

**Principle:** the extension never shows a repository the user cannot open. The org file is read-only unless GitHub says the user can write to `<org>/.github`. Every disabled action explains why and offers the alternative that works.

**1. Access levels.** Detect them on load, cache them per org, and refresh them with the index:

| Level | How to detect | Grouped view | Org groups | My groups | Sync access |
|---|---|---|---|---|---|
| **Org owner** | `GET /user/memberships/orgs/{org}` → `role: admin` | All repos the user can see (all) | Edit and commit | Yes | All rows |
| **Org file editor** (member with write on `<org>/.github`) | `GET /repos/{org}/.github` → `permissions.push: true` | Repos the user can see | Edit and commit | Yes | Rows for repos where `viewerIsAdmin` |
| **Member** (default for most people) | Membership `role: member`, no push on `.github` | Repos the user can see | **Read-only + Suggest changes** | Yes | Rows for repos where `viewerIsAdmin`; otherwise read-only plan + Copy list |
| **Outside collaborator / no org file access** | Membership 404, or `.github` not readable | Repos the user can see | Not shown (no file) | Yes, the only layer | Same as Member |
| **App not installed on the org** | The API returns no private org repos, or the installation is missing (step 2) | Public repos only, plus a banner | Read-only if `.github` is public | Yes | No |

**2. Getting access without being an admin.**
- **Normal case:** an org owner installs the GitHub App **once** for the whole org, with "All repositories" (§6). After that every member signs in with the device flow and the API returns exactly the repos that member can access. A user token only reaches what both the App and the user can reach, so a member never sees more than in GitHub's own UI.
- **App not installed yet:** show a banner on the org page: "Repository Group for Github isn't installed in <org> yet, so only public repositories are shown." It offers two actions:
  - **Ask an org owner to install it**: opens `https://github.com/apps/<app-slug>/installations/new`. Members can send an install request from there, and GitHub notifies the owners.
  - **Use a personal access token instead** (Options): a classic token with `repo` + `read:org`, or a fine-grained token whose resource owner is the org.
    - Whether the org accepts the token depends on its policy: fine-grained tokens may need owner approval, classic tokens may be blocked, and orgs with SAML SSO require authorizing the token for SSO.
    - When the API rejects the token, explain which of these applies, based on the error message.
- **Public-only mode** (no token, or a token the org rejects): index only public repos and show the banner above. Rate limits are lower; keep the parallel index at 2 concurrent requests.

**3. What changes in the UI for read-only users of the org file.**
- **Header:** a small neutral badge "**Org groups are read-only for you** · Organize in My groups or suggest a change", next to the Org groups | My groups switch. The badge is shown only on the org layer.
- **Default layer:** if My groups is not empty, open it by default. Remember the last choice per org.
- **On the org layer:**
  - **Edit group**, **New group** and logo editing open in **suggest mode**: same drawer, but the footer button reads **Suggest change** instead of Save changes.
  - **Edit YAML** opens in suggest mode: the AI round-trip and the diff work the same, and the commit button reads **Suggest change**.
  - **Suggest change**, without any write permission:
    1. copies the full proposed `repo-groups.yml` to the clipboard;
    2. opens GitHub's web editor for the file, `https://github.com/<org>/.github/edit/<default-branch>/repo-groups.yml`, in a new tab. For users without write access, GitHub turns that page into its own "fork and **Propose changes**" flow, which opens a pull request.
    3. A short guide in the drawer says: "Paste the copied file over the content, then click **Propose changes**. An org file editor reviews it."
    - **When the editor flow is not possible:** if `<org>/.github` is private and the org does not allow forking private repositories, GitHub cannot fork it for the user, and the editor flow fails. Detect it with `allow_forking: false` on `GET /repos/{org}/.github` and go straight to the alternative below.
    - **Alternative:** a link to open a new issue in `<org>/.github` with the diff list prefilled in the URL (`/issues/new?title=…&body=…`). Use it only when the text fits in about 6,000 characters; otherwise copy only.
- **On the personal layer:** everything works without restrictions (F13).
- **Copy groups to My groups:** a button on the org layer copies the org tree into the user's My groups, with names and rules, so they can start from the official structure and change it.
- **Team tags:** shown read-only. The Teams field in Edit group is hidden in suggest mode, except in the YAML text.

**4. New repository (F9) for members.**
- Creating the repository itself follows GitHub's org setting "Members can create repositories". The extension does not change that.
- The Group picker lists **My groups first**, then the org groups marked "suggest". Choosing an org group the user cannot edit:
  - files the repo in **My groups** under the same path, creating the groups if needed;
  - shows "Suggest adding it to the org file" in the post-create toast. It runs the suggest flow with the one-line change.
- The Teams field: the user's teams are pre-filled as usual. Grants run on the new repo, where the creator is usually admin. If a grant fails, the toast explains it (F9).

**5. Only what the user can access.** The repo index (F14) is built from the user's own API calls, so it naturally contains only repos the user can open. Every count, search result, AI export (`repositories:` list), diff and team page comes from that index. Never mix data from another user. The optional Action index (`repo-index.json`) can list repos this user cannot open. When it is used, drop every entry that is not confirmed by the user's own incremental or reconciliation calls before showing it, and show no names from the Action file until that check has run.

**Done when:**
1. A member without write on `thekonnen/.github` sees only the repos they can access, grouped by the org file, with the read-only badge.
2. They can build a full hierarchy in My groups for those repos, including through the AI round-trip.
3. **Suggest change** copies the YAML and opens GitHub's editor. Pasting and clicking "Propose changes" creates a PR in `thekonnen/.github`.
4. With the App not installed, the org page shows public repos and the banner with "Ask an org owner to install it".
5. Sync access only lets them apply rows for repos they administer.

## 5. Data model

### 5.1 `repo-groups.yml` (version 1)
```yaml
version: 1                 # integer, required on write; missing = 1 on read
index: api                 # optional: "api" (default) or "action" (F14, uses repo-index.json)
groups:                    # required list (may be empty)
  - name: infra            # required: the slug. ^[a-z0-9._-]+$ ; unique among siblings. Used in URLs, rules and paths
    title: "Infra"         # optional display name, any characters (e.g. "Grupo: Competição" with slug grupo-competicao)
    description: "..."     # optional string
    keywords: ["s3", "backup"]  # optional list of words (tools, topics). Only used to suggest a group for a new repo (core/suggest.ts); never changes placement
    logo: "logos/infra.png" # optional; path inside <org>/.github, or an https URL
    teams: ["core_team", { slug: "ai-squad", permission: "maintain" }]
                           # optional (F12). A plain string = that team with "push" (Write).
                           # permission: pull | triage | push | maintain | admin | <custom repository role name>
                           # Inherited by every subgroup; the closest definition of a slug wins.
    labels: ["urgent", { name: "bug", color: "d73a4a", description: "Something is broken" }]
                           # optional (C2). Default issue labels; a string = default color (ededed). Inherited; closest name wins.
    milestones: [{ title: "v1", due_on: "2026-12-31", description: "First release" }]
                           # optional (C2). Default milestones, same inheritance. Sync labels only adds what a repo lacks.
    match: ["dagsrv", "dags-*", "topic:kubernetes"]  # optional list of exact names, * patterns or topic:<github-topic> rules (a single string is accepted)
    shared: ["lib-core", "ui-*", "topic:backend"]  # optional (A3). Same rules as match (names, patterns, topic:, prop:, fork-of:), but they ALSO list the repo in this group, like a tag.
                           # Never changes the primary placement. Additive: files without it parse exactly as before.
    groups: [ ... ]        # optional nested groups, any depth (UI and AI prompt recommend ≤ 3)
```
- UI labels for permissions: `pull` = Read, `triage` = Triage, `push` = Write, `maintain` = Maintain, `admin` = Admin (GitHub's own names).
- The personal **My groups** file (F13) uses the same schema without `index` and `teams`.
- Unknown keys are ignored on read and dropped on write.
- `repositories:` is reserved (AI context) and ignored.
- The **writer** emits the canonical format: the order is `name, title, description, keywords, logo, teams, labels, milestones, match, shared, groups`; `teams` uses plain strings for `push` and the `{ slug, permission }` form otherwise; strings in double quotes; `match` in flow style (`["a", "b"]`); 2-space indentation; a leading comment line `# <org>/.github/repo-groups.yml`. See `yamlPreview()` in `mockup.js`. Write it by hand; do not ship a YAML dumper.
- The **reader** uses a real YAML parser (js-yaml), lazy-loaded.

### 5.2 Validation errors (copy from the mockup)
- `The file needs a top-level "groups:" list.`
- `groups → item N: name "X" must use lowercase letters, numbers, - _ or .`
- `Two groups are named "x" in <parent>.`
- `"x": match must be a list of names or patterns.`
- `"x": keywords must be a list of words.`
- `"x": shared must be a list of names or patterns.`
- `"x": groups must be a list.`
- `"x": teams must be a list of team slugs or { slug, permission }.`
- `"x": permission "y" must be one of pull, triage, push, maintain, admin, or a custom repository role of <org>.` (When the custom roles cannot be read, accept any non-empty name and show a warning instead.)
- Warning only (not an error): `"x": team "y" was not found in <org>.`
- YAML syntax errors: `<reason> (line N)`, with the line highlighted in the gutter.

### 5.3 Placement algorithm (must be identical everywhere: view, diff, new-repo field, AI prompt)
1. Build the group list in **post-order** (children before parents, in file order).
2. **Exact names win:** the first group in that order whose `match` contains a rule without `*` that equals the repo name (case-insensitive).
3. Otherwise, the **first group in post-order** with a `*` pattern that matches. This means the deepest match wins. Patterns are converted to `^…$` regex, `*` becomes `.*`, other characters are escaped, case-insensitive.
4. Otherwise the repo is **Ungrouped** (root).

**Topic rules (A1):** a rule `topic:foo` matches the repo's GitHub topics (case-insensitive) instead of its name. Without `*` it is exact-style (step 2), with `*` (`topic:ml-*`) it is pattern-style (step 3). The value after `topic:` must not be empty. Topics come from `topics` in the REST repo list and are stored in the repo index (`topics: string[]`).

Reference: `globRe`, `pickIn`, `ruleFor`, `assign`, `placement` in `design/mockup/mockup.js`.

**Shared memberships (A3, additive).** The four steps above give each repo exactly one **primary** group. A group may also declare `shared` rules (same glob semantics, exact or `*`). A repo that matches a group's `shared` rule is additionally **listed** in that group (`sharedPlacement()` in `core/placement.ts` returns `primary` plus `secondary: repo -> [group keys]`). Rules:
- The primary placement is untouched. Ungrouped detection, the "grouped" counts, the diff's `→` moves, the New repository destination and **team target access / the sync plan (§5.5) use the primary placement only**. A repo listed in two groups with different team tags would have two possible targets; using the primary keeps the target unambiguous and never grants access by accident.
- A group that already contains the primary group (itself or an ancestor) is skipped: the repo is already listed there recursively.
- `shared` rules take every rule kind `match` takes (names, `*` patterns, `topic:`, `prop:`, `fork-of:`), tested against the whole repo, and are validated like `match`.
- **Move vs. Also list in…** (drag & drop and the row/selection menus): *Move* changes the home (exact name in `match`; it also removes the now-redundant exact name from the `shared` of the destination and its ancestors). *Also list in…* (Alt/Option-drag) only adds the exact name to the destination's `shared` (`shareRepos()`), skipping repos that live there or below it and repos it already lists. A move to Ungrouped reports the groups that still list the repo through `shared`; a checkbox (on by default) also removes the exact names, rules only warn. The confirmation dialog notes how the target team access changes with the new home (informational, `teamTargetChanges()`); nothing is granted or removed. Shared rows have no checkbox or drag handle: selection and drag always refer to the primary row. A shared row is shown as a **link** (link icon, dashed look, chip "linked from <primary>" that opens the original). Its **Remove link** button (`unshareRepos()`, Edit kind `unshare`, commit `stop listing <repo> in <path>`) removes only the exact name from that group's `shared`; the home is never touched. When only a rule lists the repo, the dialog points to Edit group instead of committing.
- Counts: a repo counts once per group, never twice in a parent or in the root total. A shared repo is shown inside each group with a muted "also in <primary path>" label; search shows it once.

### 5.4 Diff (YAML editor)
Compare the saved and the draft tree:
- groups added or removed (by full path);
- per surviving path: description, logo, teams, rules and shared-rules changes;
- per repo: placement changes, and changes of the extra (shared) memberships.

Reference: `diffTrees`.

### 5.5 Effective teams and the sync plan (F12)
```
effectiveTeams(group):
  map = {}
  for g in [root's child … group]:      # top-down along the path
    for t in g.teams: map[t.slug] = { permission: t.permission, from: path(g) }
  return map                            # closest definition wins

rank = { none: 0, pull: 1, triage: 2, push: 3, maintain: 4, admin: 5 }

syncPlan(teamSlug):                     # rows for the Sync access drawer
  for repo in index (not archived):
    g = orgPlacement(repo)              # §5.3 on the org tree; skip if ungrouped
    target = effectiveTeams(g)[teamSlug]; skip if none
    current = teamAccess[teamSlug][repo.name] or "none"
    if rank[current] < rank[target.permission]: yield { repo, team, current, target }
```
Never yield removals or downgrades. Put this in `core/teams.ts`, pure and unit tested.

## 6. Authentication

- Use a **GitHub App** with the **device flow** (no client secret in the extension; works in every browser):
  1. Background worker: `POST https://github.com/login/device/code` with `client_id`. Show `user_code` and a button opening `https://github.com/login/device`.
  2. Poll `POST https://github.com/login/oauth/access_token` (`grant_type=urn:ietf:params:oauth:grant-type:device_code`) at the given `interval`; handle `slow_down` and `expired_token`.
  3. Store the token in `storage.local`, readable only by the background worker. Content scripts never see the token: they send messages and the background worker calls the API.
- These endpoints do not support CORS from web pages. Call them **only from the background worker**, which is allowed by `host_permissions` for `https://github.com/*`.
- **GitHub App settings** (document them in the README; the user creates the app):
  - "Enable Device Flow": on;
  - "Expire user authorization tokens": **off**, so no client secret is needed for refresh. Otherwise re-run the device flow on 401.
  - **Permissions:**
    - Repository → Metadata: Read (listing);
    - Repository → Contents: Read & write (only used on `<org>/.github`);
    - Repository → Issues: Read & write (open counts; C2 adds default labels and milestones to repositories), Pull requests: Read;
    - Repository → Administration: Read & write (F12: add teams to repositories);
    - Organization → Members: Read (F12: see teams, list teams and their repositories).
  - **Adding a team to a repository** (`PUT /orgs/{org}/teams/{team_slug}/repos/{owner}/{repo}`, confirmed in GitHub Docs → "REST API endpoints for teams") needs **all three** at once:

    | Scope | Permission | Level |
    |---|---|---|
    | Repository | Administration | Read & write |
    | Organization | Members | Read |
    | Repository | Metadata | Read (mandatory on every App) |

    Things to know:
    - **Administration (write) is the sensitive one.** It gives the App admin power on the repository, including settings, branch protection and collaborators. The endpoint requires that level; there is no narrower alternative. Say this plainly in the README and in the store listing, and explain that the extension only uses it to add teams (§7 lists the only write calls).
    - **Members (read) is an organization permission**, not a repository one. If the App only has repository permissions, the call fails, because the App cannot see the team.
    - **The App must have access to the target repository:** the installation covers "All repositories", or the repo is in "Selected repositories". F1 already requires "All repositories".
    - **The repository must belong to the organization**, or be a direct fork of one of its repositories. Otherwise the API returns **422**.
    - **Changing the permissions of an installed App needs approval.** After the App's permissions change, an org owner must accept the update on the installation. Until then tokens keep the old permissions and calls return **403 or 404**. Detect this case and show: "Repository Group for Github needs new permissions in <org>. An org owner must accept the update in **Settings → GitHub Apps**." Link to `https://github.com/organizations/<org>/settings/installations`.
    - **The `permission` body field** accepts `pull`, `triage`, `push`, `maintain`, `admin`, or the **name of a custom repository role** of the organization. If it is omitted, the team's default permission applies. The extension always sends it explicitly.
    - **Use only the org + slug route.** Do not use the legacy `PUT /teams/{team_id}/repos/{owner}/{repo}`, which GitHub is deprecating. The `/organizations/{org_id}/team/{team_id}/…` form is still valid but not needed.
    - **Troubleshooting 403:** read the `X-Accepted-GitHub-Permissions` response header. It lists the permissions the endpoint expected. Log it with `console.debug('[RG] …')` and include it in the error detail of the Sync access row.
    - Endpoint permissions can change between API versions. Re-check this table against GitHub Docs before each release.
  - **Who can sync access (both are supported):**
    - **Org owners** are admins on every repository. They can apply every row.
    - **Repository admins** can apply rows only for the repositories they administer.
    - Anyone else can see the sync plan but every row fails with the admin error (F12). In that case show the plan read-only, with **Copy list** (repo, team, permission as text) to send to an owner.
    - Detect the role up front so the UI does not offer rows that will fail:
      - org owner: `GET /user/memberships/orgs/{org}` returns `role: admin`;
      - repo admin: the index's `permissions.admin` from the REST repo list.
    - Rows the user cannot apply start **unchecked** and show "Needs an org owner or a repo admin".
  - It must be **installed on the org with access to all repositories**, or user tokens will not see them. Explain this in the empty state when the repo count looks incomplete.
- **Fallback:** a personal access token pasted in Options: fine-grained with the same permissions, or classic with `repo` + `read:org`. Org policies can require owner approval for fine-grained tokens, block classic tokens, or require SSO authorization (F15 explains these to members).
- **Members without admin rights** never need extra rights. The only owner action is installing the App once. Their access levels and fallbacks are in F15.
- Put the client id in `src/config.ts`. Never commit secrets.
- **Open item:** confirm with the user who owns or creates the GitHub App and which client id to use.

## 7. Writing to GitHub (commits)

- **Single file** (YAML only): `PUT /repos/{org}/.github/contents/repo-groups.yml` with the base64 content, `message`, and the `sha` (omit `sha` when creating). The default branch is used.
- **YAML + logo in one commit:** use the Git Data API:
  1. `GET ref`;
  2. `POST blobs` for the PNG and the YAML;
  3. `POST trees` with base_tree;
  4. `POST commits`;
  5. `PATCH ref`.

  - For F5/F6/F7/F9, re-apply the single change to the fresh tree and retry once.
  - For F8, show "The file changed on GitHub since you opened it" with **Reload and keep my text**, which re-runs the diff against the fresh file.
- **Protected default branch:** if the push is rejected, explain it and offer to open a PR instead. Create the branch `repo-groups/<timestamp>` and open the PR via the API. This can come after the MVP; until then, show a clear error.

## 8. GitHub API usage

GraphQL `POST https://api.github.com/graphql`:
```graphql
query ($org: String!, $after: String) {
  organization(login: $org) {
    repositories(first: 100, after: $after, orderBy: {field: PUSHED_AT, direction: DESC}) {
      totalCount
      pageInfo { hasNextPage endCursor }
      nodes {
        name description isPrivate isFork isArchived pushedAt url
        primaryLanguage { name color }
        stargazerCount forkCount
        issues(states: OPEN) { totalCount }
        pullRequests(states: OPEN) { totalCount }
      }
    }
  }
}
```
- Archived repos: hide them by default (as GitHub does under "All"); show them in an "Archived" tab later.
- Respect `X-RateLimit-*` headers; back off and show cached data when limited.
- REST for contents/commits (§7).
- **Index (F14):** REST `GET /orgs/{org}/repos?type=all&sort=pushed&direction=desc&per_page=100&page=N`. It supports page numbers, so pages can be fetched in parallel after the first one returns `Link: rel="last"`. GraphQL cursors cannot be parallelized, which is why the index uses REST. The GraphQL query above is used only for lazy detail counts (split issues and PRs) on small groups, with aliases (`r0: repository(owner:, name:) {…}`) in batches of 50.
- **Teams (F12):**
```graphql
query ($org: String!, $after: String) {
  organization(login: $org) {
    teams(first: 100, after: $after) {
      pageInfo { hasNextPage endCursor }
      nodes { slug name privacy parentTeam { slug } members { totalCount } }
    }
  }
}

query ($org: String!, $slug: String!, $after: String) {
  organization(login: $org) {
    team(slug: $slug) {
      repositories(first: 100, after: $after) {
        pageInfo { hasNextPage endCursor }
        edges { permission node { name } }   # permission: READ | TRIAGE | WRITE | MAINTAIN | ADMIN
      }
    }
  }
}
```
  Map GraphQL permissions to YAML values: READ→pull, TRIAGE→triage, WRITE→push, MAINTAIN→maintain, ADMIN→admin. Fetch team repositories only for teams that appear in the YAML, plus the team whose page is open.
- **Grant access:** REST `PUT /orgs/{org}/teams/{team_slug}/repos/{owner}/{repo}` with body `{"permission": "push"}` → 204. Never call `DELETE` on that endpoint. Required App permissions and error cases: §6.
- **Custom repository roles:** `GET /orgs/{org}/custom-repository-roles` returns each role's `name` and `base_role`. The sync plan ranks a custom role by its `base_role`. If the list cannot be read (the user is not an owner), a custom-role target is only proposed when the team has no access at all.

## 9. Architecture

**Stack**
- [WXT](https://wxt.dev) (MV3; builds both Chromium and Firefox);
- TypeScript (strict);
- **Preact** for UI (≈4 KB). Plain DOM is also fine for small pieces;
- **Vitest** and **Playwright**.
- No CSS framework, no icon library: copy the Octicon SVG paths you need (they are already in `ICON` in `mockup.js`) into `src/ui/icons.ts`.
- js-yaml is the only runtime dependency besides Preact, and it is lazy-loaded.

**Suggested layout**
```
src/
  entrypoints/
    background.ts            # auth, API calls, caching, commits, pending-new-repo watcher
    github.content.ts        # matches https://github.com/*; routes to features by URL
    popup/                   # sign-in state, org list
    options/                 # token, cache, per-org prefs
  core/                      # pure, framework-free, 100% unit tested
    glob.ts placement.ts yaml-read.ts yaml-write.ts validate.ts diff.ts highlight.ts ai-prompt.ts
    teams.ts                 # effectiveTeams, syncPlan, permission mapping (F12)
    index-sync.ts            # page planning, merge, incremental stop rule, reconciliation (F14)
    layers.ts                # org vs My groups selection, #~my/ hash parsing (F13)
  github/
    api.ts                   # typed messages → background
    selectors.ts             # ALL GitHub DOM selectors live here, with fallbacks
    navigation.ts            # turbo:load / popstate / pjax detection, idempotent mount/unmount
  features/
    grouped-view/ sidebar-tree/ group-drawer/ logo-cropper/ yaml-editor/ new-repo-field/
    team-page/ sync-access/ my-groups/ index-status/
  storage/
    idb.ts                   # tiny IndexedDB wrapper (no library): repo index, logo cache
    sync-chunks.ts           # split/join My groups across storage.sync items
  ui/
    icons.ts components (Button, Drawer, Toast, Avatar, Picker, Tabs, Stat)
  styles/
    tokens.css (copy of design/tokens.css) + component CSS (port from design/mockup/styles.css, prefixed .rg-)
public/_locales/en/messages.json
```

**DOM integration rules**
- GitHub navigates with Turbo, without full page loads. Listen for `turbo:load`/`turbo:render` and `popstate`, plus a cheap URL-change check as a safety net. Mount and unmount idempotently, keyed by URL.
- Mount the UI in a container `<div class="rg-root">` inserted **next to** GitHub's list (and hide GitHub's list via a class), rather than rewriting GitHub's nodes. Toggle back by removing the class.
- Prefix every class with `rg-`, and keep the CSS scoped under `.rg-root`. Shadow DOM is acceptable for the drawers and popovers if style leakage becomes a problem; the tokens then go on `:host`.
- Keep every selector in `github/selectors.ts`, with 2–3 fallbacks each. **If a mount point is not found, do nothing**, and log once with `console.debug('[RG] …')`. Never throw on GitHub pages.
- Do not take over pages that are not ours: only `/orgs/<org>/repositories`, `/orgs/<org>/teams/<slug>/repositories` (F12), `/organizations/<org>/repositories/new`, `/new`, and repo pages (for the post-create toast).

**Permissions (manifest)**
- `permissions`: `storage`.
- `host_permissions`: `https://github.com/*`, `https://api.github.com/*`.
- `optional_host_permissions`: `https://*/*` (only requested for a logo link's origin, at click time).
- Firefox: `browser_specific_settings.gecko.id` and `strict_min_version` with MV3 support.

## 11. Design system

- **Look:** GitHub Primer. Copy spacing, radius, typography and component looks from `design/mockup/styles.css`. Main values:
  - buttons: 32px tall, 6px radius;
  - group avatar: 56px with 10px radius;
  - row avatar: 32px with 6px radius;
  - text: 14px body, 12px meta.
  - The system font stack and mono stack are in tokens.
- **Colors:** only through `--rg-*` tokens from `design/tokens.css`.
  - On github.com these resolve to GitHub's own Primer variables, so all GitHub themes, including dimmed and high-contrast, just work.
  - Do not add our own `prefers-color-scheme` logic in content scripts: GitHub decides via `data-color-mode` on `<html>`.
- **Marker for extension UI:** the small purple square plus "Repository Group" text tag (`--rg-ext`). Use it wherever we inject into a GitHub page (sidebar heading, New repository Group field).
- **Letter avatars:** five tones (`--rg-av1…5`). The tone is chosen by the sum of the char codes of the group name, mod 5 (`avClass` in the mockup).
- **Copy:** plain, active voice, says what will happen ("Apply and commit", "Use this crop"). Errors say what went wrong and how to fix it. Reuse the mockup strings.
- **Accessibility:**
  - every control is keyboard reachable with visible focus;
  - the drawers are `role="dialog"` with `aria-modal`, close on Esc and return focus;
  - the picker is a `listbox` using `aria-activedescendant`;
  - the toast is `role="status"`;
  - respect `prefers-reduced-motion`.
- **Responsive:** must work at about 400px wide (GitHub mobile web). At that width the rows' right column is hidden and the drawers are full width.
